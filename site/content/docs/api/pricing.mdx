All costs in the usertrust SDK are denominated in **usertokens** (UT).

**1 UT = $0.0001** (one basis point of a cent).

A budget of `100_000` UT equals $10.00. A budget of `1_000_000` UT equals $100.00.

## Pricing Table

The SDK includes a 42-model pricing table in `ledger/pricing.ts`, current as of
`PRICING_TABLE_VERSION = "2026-10-08"` (see [PRICING_TABLE_VERSION](#pricing_table_version)).
Rates are in usertokens per 1,000 LLM tokens, across **four tiers**: input (fresh prompt tokens),
output, cache-read (cache-hit prompt tokens), and cache-write (cache-creation prompt tokens). A
`—` means the provider publishes no rate for that tier — it is **not** free; see
[Cache tiers and the fallback invariant](#cache-tiers-and-the-fallback-invariant) below.

### 1-hour cache writes

`ModelRates.cacheWrite1hPer1k` is the 1-hour write rate. Every Anthropic row carries it
explicitly (the page's "1h cache writes" column). `cacheWriteTokens` is the TOTAL cache-write
count, and the 1-hour tokens are a **subset** of it (never added to it): the 5-minute term is
`cacheWriteTokens - cacheWrite1hTokens`. A 1-hour count above the total is clamped to it, and a
1-hour count with no write total prices nothing at the 1-hour rate; sent alone to a headless
`settle()` it is not reported usage, so the settle meters at the pre-call estimate. A custom row that omits `cacheWrite1hPer1k`
resolves, in one place (`effectiveCacheWrite1hRate`), to the dearer of its 5-minute write rate and
2x `inputPer1k`: a silent row is never billed below 2x input.

Where the split comes from: the Anthropic `usage.cache_creation` breakdown, on both stream
surfaces and the non-stream path; headless `settle()` takes `cacheWrite1hTokens`; `usertrust-server`
accepts it on `POST /v1/settle` and lists `cache-write-1h` in `/v1/health` `capabilities` (an older
server strips the key, so a client sends it only when the capability is listed). A payload that
carries only the flat `cache_creation_input_tokens` total, and a host with no TTL split (the
OpenClaw plugin's usage), prices at the 5-minute rate.

**On the receipt**, when the call wrote 1-hour cache: a ROOT field
`cacheWrite1h: { tokens, ratePer1k }`, never inside `usage` or `pricing.appliedRates` (the v2 schema
closes both). It is absent otherwise, so every other receipt is unchanged. An auditor's recompute
splits the write term: `(usage.cacheWriteTokens - cacheWrite1h.tokens) x appliedRates.cacheWritePer1k +
cacheWrite1h.tokens x cacheWrite1h.ratePer1k`.

## Cache tiers and the fallback invariant

`ModelRates` carries two optional fields beyond `inputPer1k`/`outputPer1k`:

```typescript
interface ModelRates {
  inputPer1k: number;
  outputPer1k: number;
  cacheReadPer1k?: number;  // absent ⇒ prices at inputPer1k, never 0
  cacheWritePer1k?: number; // absent ⇒ prices at inputPer1k, never 0
  cacheWrite1hPer1k?: number; // 1-hour writes; absent ⇒ the dearer of cacheWritePer1k and 2 × inputPer1k
}
```

**Absent means "no published rate," not "free."** `costFromRates` resolves an absent (or
non-finite/negative) cache rate to the model's `inputPer1k` — this is the one and only rate
resolution site in the SDK. A model that omits `cacheWritePer1k` still bills cache-write tokens,
at the same rate as fresh input.

This is deliberately fail-safe: understating a bill is the dangerous direction (a budget that
looks fuller than the real invoice), so an unmodeled cache tier defaults to the *conservative*
price, never to zero. Never treat an absent field as a discount.

## Fallback Rate

Models not in the pricing table are priced at the **highest rate the table publishes** ("fail
dearest"). An unknown id over-counts visibly instead of under-counting silently:

| Direction | Rate (per 1K tokens) |
|-----------|---------------------|
| Input | 250 UT |
| Output | 1250 UT |
| Cache write | 312.5 UT (5m) / 500 UT (1h) |
| Cache read | 250 UT (the input rate; no cache discount is assumed) |

These are the maxima over the table (today `claude-mythos-preview`, $25 / $125); a test recomputes them,
so a dearer row cannot be added without raising the fallback. A fallback-priced record carries
`rateSource: "fallback"` and `unknown: true`. An unrecognized model isn't known to be
Anthropic-shaped, so no cache-read discount is attached. Set `unknownModelPolicy: "deny"` to refuse
an unknown model instead of metering it. The fallback is the dearest rate the table KNOWS; it cannot bound a model the table does not list that costs more than every row in it (`claude-mythos-preview` was exactly that case before it got its own row). For a hard budget, `unknownModelPolicy: "deny"` is the guarantee.

## Model Matching

`getModelRates()` resolves a model id in this order:

1. an **exact** row;
2. the id with exactly one trailing date suffix stripped — `-YYYYMMDD` (`claude-haiku-4-5-20251001`)
   or `-YYYY-MM-DD` (`gpt-4o-2024-08-06`) — then exact;
3. the fallback rate, flagged `rateSource: "fallback"`, `unknown: true`.

There is no prefix matching: `claude-sonnet-5-5` is a different, separately priced model from
`claude-sonnet-5`, and a longer id that merely begins with a table key used to be billed at that
key's row while the receipt claimed an exact table match. The exact row is tried first because a
dated snapshot can cost **more** than its alias: `gpt-4o-2024-05-13` is $5 / $15 per MTok against
`gpt-4o`'s $2.50 / $10, so it has its own row and is never reduced to the alias. A dated snapshot
with no row of its own is metered at its base row, which assumes it is priced like its alias.

**Residue (priced at the fallback, flagged):** Gemini `…-preview-MM-DD` ids, a seven-digit or
non-numeric suffix, `-fast`, and Bedrock `anthropic.…:0` / Vertex `…@…` ids. `isModelPriced()` is
stricter on purpose: it checks for an exact key (or custom rate) only, so a dated snapshot meters
at its base row but is not "priced" for a caller that must refuse what it cannot price exactly.

```typescript
getModelRates("claude-fable-5")           // exact match → { 100, 500 }
getModelRates("claude-fable-5-20260301")  // dated snapshot → claude-fable-5 → { 100, 500 }
getModelRates("gpt-4o-2024-08-06")        // dated snapshot → gpt-4o → { 25, 100 }
getModelRates("gpt-4o-2024-05-13")        // exact row, priced above its alias → { 50, 150 }
getModelRates("claude-fable-5-1")         // its own row → { 100, 500, cache read 2.5 }
getModelRates("claude-opus-5-fast")       // unknown → fallback → { 250, 1250 }
```

## Functions

### getModelRates()

```typescript
function getModelRates(model: string): ModelRates
```

Look up the four-tier rates for a model. Resolves an exact row, then the id with one date suffix stripped, then the fallback rate (never a prefix match).

### costFromRates()

```typescript
function costFromRates(
  rates: ModelRates,
  inputTokens: number,
  outputTokens: number,
  cacheReadTokens?: number,  // default 0
  cacheWriteTokens?: number, // default 0; the TOTAL written (5m + 1h)
  cacheWrite1hTokens?: number, // default 0; the 1-hour SUBSET of cacheWriteTokens
): number
```

Compute usertoken cost across all four tiers from an explicit `ModelRates`. The four counts are
expected to be **disjoint** — cached tokens must already be separated out of `inputTokens` before
this is called, or they are double-counted. Absent cache rates resolve to `inputPer1k` (see [Cache
tiers and the fallback invariant](#cache-tiers-and-the-fallback-invariant)); the result is floored
at 1 usertoken, same as `estimateCost()`.

```typescript
// 1,000 fresh input + 500 output + 2,000 cache-read tokens on claude-fable-5
costFromRates(getModelRates("claude-fable-5"), 1000, 500, 2000, 0)
// → Math.max(1, Math.ceil((1000 * 100)/1000 + (500 * 500)/1000 + (2000 * 10)/1000))
// → Math.max(1, Math.ceil(100 + 250 + 20))
// → 370 UT
```

Each tier is computed as `(tokens × ratePer1k) / 1000` — **multiply before dividing**. This is the
same order the [receipt schema](https://usertrust.ai/schemas/receipt.v2.schema.json) publishes as
`ceil(sum(counts × rates / 1000))`, and it is load-bearing rather than stylistic: in IEEE-754 the
divide-first form `(tokens / 1000) × ratePer1k` can land a ulp above an integer (560 cache-write
tokens at 12.5/1k give `7.000000000000001`), which `Math.ceil` then rounds to a whole extra
usertoken. Reconciling against a receipt with the published formula reproduces the charged cost
exactly, on every input.

### estimateCost()

```typescript
function estimateCost(model: string, inputTokens: number, outputTokens: number): number
```

Two-tier convenience wrapper around `costFromRates()` for callers that don't have a cache split —
`cacheReadTokens`/`cacheWriteTokens` default to 0. The result is always at least 1 (floor to
prevent zero-amount transfers in TigerBeetle).

```typescript
// 1,000 input tokens + 500 output tokens on claude-fable-5
estimateCost("claude-fable-5", 1000, 500)
// → Math.max(1, Math.ceil((1000 * 100)/1000 + (500 * 500)/1000))
// → Math.max(1, Math.ceil(100 + 250))
// → 350 UT
```

### estimateInputTokens()

```typescript
function estimateInputTokens(messages: unknown[]): number
```

Estimate the input token count from a messages array before the LLM call. Uses a heuristic of approximately 4 characters per token with a 1.5x safety margin so the PENDING hold exceeds actual cost in the majority of cases.

This function handles:
- String content and multi-part content blocks
- Nested arrays (tool result payloads)
- Per-message overhead (role, structure)
- Tool-call overhead

Returns at least 1. This estimate never models cache state — see [Documented
approximations](#documented-approximations).

## ModelRates

```typescript
interface ModelRates {
  inputPer1k: number;        // usertokens per 1,000 fresh input tokens
  outputPer1k: number;       // usertokens per 1,000 output tokens
  cacheReadPer1k?: number;   // usertokens per 1,000 cache-hit tokens; absent ⇒ inputPer1k
  cacheWritePer1k?: number;  // usertokens per 1,000 cache-creation tokens; absent ⇒ inputPer1k
  cacheWrite1hPer1k?: number; // 1-hour cache writes; absent ⇒ max(cacheWritePer1k, 2 × inputPer1k)
}
```

### PRICING_TABLE_VERSION

```typescript
const PRICING_TABLE_VERSION: string  // e.g. "2026-08-09"
```

Date-stamped version of the built-in `PRICING_TABLE`, bumped whenever any entry's rates change.
Recorded on every settled receipt (`receipt.pricing.tableVersion`) alongside the resolved
rates (`receipt.pricing.appliedRates`) so a metered cost can be reproduced exactly against the table
version that priced it, independent of the SDK version currently installed.

## Hold sizing and the cache-write premium

The PENDING hold reserves the input leg at the dearest write rate the call can produce, not
`inputPer1k` alone. A cache write can price *above* plain input — Anthropic's 5-minute write is
1.25x, the 1-hour write 2x — so sizing the hold off `inputPer1k` alone understates the reserve for
any call that turns out to write to cache. The hold covers the worst case **this request** can
produce:

- the governed `trust()` path reads the request: it reserves the 1-hour rate only when the request
  declares a 1-hour TTL (a `cache_control` block with `ttl: "1h"` anywhere in it), and otherwise holds
  at `max(inputPer1k, effectiveCacheWriteRate(rates))` exactly as before;
- the headless `authorize()` path runs before the call and cannot see the TTLs, so it reserves the
  dearest write rate (the 1-hour one) for the input leg and for any stated `estimatedCacheWriteTokens`. Only a row that publishes a 1-hour
  rate reserves it, so a model with no 1-hour tier holds as before; operator-owned rates
  (`customRates`, local rates, the fallback) with no `cacheWrite1hPer1k` reserve the derived 2x input,
  as their 1-hour tokens are metered at that rate.

**Consequence:** holds on cache-writing workloads run roughly 25% fatter than an input-only hold
would size them, and **headless holds on Anthropic models run about 60% fatter on the input leg**
(2x input against 1.25x), so a 402 near the budget comes sooner. The trust() path pays the extra only
for a request that declares a 1-hour TTL. Warm (cache-hit-heavy) calls settle well below the hold and release the
difference — this is conservative, not wasted budget. A caller supplying an exact
`estimatedInputTokens` for a call that turns out cache-cold can still see the settle capped at the
hold (`settlement_shortfall`, see `AGENTS.md`'s Money invariants) if the actual write premium
exceeds even the widened reserve.

## Documented approximations

Reconciliation against a provider's own invoice is **approximate**, not exact — a receipt's `cost`
exactly reproduces usertrust's own configured metered cost (counts × `appliedRates`, per-call
`ceil`, 1-UT floor), but not necessarily the provider's bill line-for-line, because:

1-hour cache writes are priced at the 1-hour rate only when the provider reports the 5m/1h split
(a flat write total, or a host with no TTL split, bills at the 5-minute rate); long-context, service-tier, regional, modality, and cache-STORAGE charges (Gemini
hourly storage, prompt-size-dependent rates; GPT-5.4 long-context uplifts) not modeled — fixed
per-model rates by design (`claude-haiku-5-5` is priced at its over-100,000-token tier, which
overstates every shorter prompt 5×); fast mode is not priced (Opus 5.5 fast is $8 / $40, Opus 5 and
Opus 4.8 fast $10 / $50; `speed` is a usage field, not a model id); per-call `ceil` + 1-UT floor
differs from provider-side aggregation. Estimates never model cache state.

## Cost Estimation Flow

During the [two-phase spend lifecycle](/docs/concepts/two-phase-spend), costs are estimated twice:

1. **Before the call (PENDING):** `estimateInputTokens()` produces a conservative input estimate. Combined with `max_tokens` for the output estimate and the cache-write premium guard above, the SDK calculates the hold amount. The 1.5x safety margin (plus the write-premium guard) means the hold usually exceeds actual cost.

2. **After the call (POST):** Actual token counts from the provider response (or accumulated from stream chunks), split into all four tiers, produce the real cost via `costFromRates()`. The difference between the hold and the actual cost is released back to the available budget.
