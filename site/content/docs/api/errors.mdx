title: Errors
description: Seven domain error classes with structured hints and documentation URLs.
---

usertrust defines seven domain-specific error classes. All extend `Error` and include structured `hint` and `docsUrl` properties for actionable diagnostics.

## Catching Errors

```typescript
import {
  InsufficientBalanceError,
  PolicyDeniedError,
  LedgerUnavailableError,
} from "usertrust";

try {
  const { response, receipt } = await client.messages.create({
    model: "claude-fable-5",
    max_tokens: 1024,
    messages: [{ role: "user", content: "Hello" }],
  });
} catch (err) {
  if (err instanceof InsufficientBalanceError) {
    console.log(`Need ${err.required} UT, have ${err.available} UT`);
    console.log(err.hint);
  }
  if (err instanceof PolicyDeniedError) {
    console.log(`Blocked: ${err.reason}`);
  }
  if (err instanceof LedgerUnavailableError) {
    console.log(`TigerBeetle down: ${err.cause_message}`);
  }
}
```

Every error class follows the same pattern: a descriptive message, a `hint` with a suggested fix, and a `docsUrl` pointing to detailed documentation.

## InsufficientBalanceError

Thrown when the requested LLM call would exceed the remaining budget.

```typescript
class InsufficientBalanceError extends Error {
  readonly userId: string;
  readonly required: number;    // usertokens needed
  readonly available: number;   // usertokens remaining
  readonly hint: string;
  readonly docsUrl: string;
  readonly auditEventHash?: string;   // the `ledger_rejected` event's hash
  readonly auditDegraded?: boolean;   // the append failed (and was dead-lettered, when that write succeeded)
}
```

**When it fires:** During the PENDING hold phase, before the LLM call is forwarded to the provider. No tokens are consumed.

**Hint:** `"Increase the budget in trust() options or add funds via the ledger."`

---

## PolicyDeniedError

Thrown when a policy rule or PII detector blocks the request.

```typescript
class PolicyDeniedError extends Error {
  readonly reason: string;
  readonly hint: string;
  readonly docsUrl: string;
  readonly auditEventHash?: string;   // the `policy_denied` event's hash
  readonly auditDegraded?: boolean;   // the append failed (and was dead-lettered, when that write succeeded)
}
```

**When it fires:** During policy evaluation, before the LLM call. The `reason` field describes which rule or PII type triggered the denial. On any client (Anthropic, OpenAI or Google) it also fires when you call an SDK method usertrust does not govern and does not list as free: the `reason` starts `ungoverned_method: <path>` (for example `ungoverned_method: embeddings.create`), the promise rejects without calling the SDK, and `trust({ allowUngoverned: ["<path>"] })` lets that method through, audited as `ungoverned_call`.

**Hint:** `'Check your policy rules in .usertrust/policies/default.yml, or set "pii": "warn" in .usertrust/usertrust.config.json (or pass { pii: "warn" } to trust()) to downgrade PII enforcement.'`

To change PII enforcement, set `pii` in the config file `trust()` reads: `.usertrust/usertrust.config.json` by default, or the file you pass as `configPath` (which is read instead, so edit that one), or pass `pii` to `trust()` itself (e.g. `{ pii: "warn" }`), which overrides the file.

## The denial correlation handle

Both denial errors above carry `auditEventHash` — the hash of the chain event
the governor wrote when it refused the call. It is the join between the
exception your code logged and the record an auditor reads: `policy_denied` for
a governor decision (a policy rule, a budget-family rule, PII, injection, an
unpriceable model, or a refused ungoverned SDK method on any provider), `ledger_rejected` for the ledger's own atomic refusal of the
hold.

```typescript
try {
  await client.messages.create({ /* ... */ });
} catch (err) {
  if (err instanceof PolicyDeniedError) {
    // Quote this in your incident ticket; `usertrust verify` can find it.
    console.log(`denied, chain event ${err.auditEventHash ?? "(none)"}`);
  }
}
```

The two fields answer different questions, and you need both:

| `auditEventHash` | `auditDegraded` | What happened |
|---|---|---|
| set | absent | The denial is on the chain, at that hash. |
| set | `true` | The event **is** on the chain at that hash, but the write reported failure — the log was fsync'd and the `.meta` sidecar was not. The handle is usable; run `usertrust verify` on the vault. |
| absent | `true` | The append was attempted, nothing durable landed, and the payload was dead-lettered to `.usertrust/dlq/` when that write succeeded. There is no chain record. |
| absent | absent | No append was attempted — an error built by hand, or thrown by a version before denial events existed. |

A failed denial-append never changes the error you receive. `audit.failClosed`
exists to stop an unaudited **spend** from settling; a denial already refused
the call and moved no money, so escalating here would only replace an
actionable, typed denial with an `AuditDegradedError` and hide *why* the call
was refused.

**Indirect callers do not receive the handle yet.** `usertrust-server` and the
ACS adapter convert the error to a wire response and do not forward
`auditEventHash` today; the field is on the in-process error object only.

## AccountNotFoundError

Thrown when the TigerBeetle account for the given user does not exist.

```typescript
class AccountNotFoundError extends Error {
  readonly userId: string;
  readonly hint: string;
  readonly docsUrl: string;
}
```

**When it fires:** During ledger initialization or the first spend attempt.

**Hint:** `'Run "npx usertrust init" to create accounts, or verify the userId matches your config.'`

---

## IdempotencyConflictError

Thrown when a transfer with the same ID has already been submitted to TigerBeetle.

```typescript
class IdempotencyConflictError extends Error {
  readonly key: string;
  readonly hint: string;
  readonly docsUrl: string;
}
```

**When it fires:** During the PENDING hold phase, if the generated `transferId` collides with an existing transfer.

**Hint:** `"This transfer was already submitted. Use a unique transferId for retries."`

---

## LedgerUnavailableError

Thrown when TigerBeetle is unreachable. The LLM call is **not** forwarded to the provider.

```typescript
class LedgerUnavailableError extends Error {
  readonly cause_message: string;
  readonly hint: string;
  readonly docsUrl: string;
}
```

**When it fires:** Before any LLM call, during the connection check or PENDING hold attempt. This is failure mode 15.4 -- no tokens are at risk because no hold was placed.

**Hint:** `'Start TigerBeetle 0.17.x (tigerbeetle format … then tigerbeetle start --addresses=<address>) or use { dryRun: true } to skip the ledger.'`, where `<address>` is the ledger the governor was configured with (`127.0.0.1:3001` by default).

<Callout type="warn">
`usertrust tb start` does not manage TigerBeetle in this version: it prints the same
format and start commands. Follow the [CLI page's `usertrust tb` section](/docs/cli#usertrust-tb)
to run a node yourself, or pass `{ dryRun: true }` to skip the ledger entirely.
</Callout>

<Callout type="warn">
When TigerBeetle is unreachable, usertrust refuses to forward the request. This is by design -- without a ledger, budget enforcement is impossible.
</Callout>

## AuditDegradedError

Thrown (or flagged) when an audit chain write fails. Usually that is after the LLM call and ledger settlement both succeed. Under `audit.failClosed` a `trust()` client throws it earlier in two cases (below): at the start of a call on a client whose audit writer is already degraded, before anything is charged, and when the call's own primary record (the `llm_call` event, or an action's own event) fails to append, before the ledger POST.

```typescript
class AuditDegradedError extends Error {
  readonly cause_message: string;
  readonly hint: string;
  readonly docsUrl: string;
}
```

**When it fires:** Usually after the LLM call succeeds and the ledger POST settles. This is failure mode 15.3. The response is still returned to the caller with `auditDegraded: true` on the receipt (except that a failed warn-mode `injection_detected` append is swallowed without marking the call or its receipt). The failed event is written to the dead-letter queue when that write succeeds. Under `audit.failClosed`, a failed primary record (the call's own `llm_call` event, or an action's own event) refuses the call before its POST, and the hold is released by a void request (the void is best-effort: see the callout below); a failure of any later record is refused only after the charge posts. Also under `audit.failClosed`, a `trust()` client whose audit writer was already degraded by an earlier failed write throws it at the start of every later call instead: the call is refused before it reaches the provider, and nothing is charged. Recreate the client after fixing the audit directory.

**Hint:** `"Check disk space and permissions on the .usertrust/audit/ directory."`

<Callout type="info">
By default usertrust does not fail a call because the audit write degraded: if the LLM call succeeded and the ledger settled, the response is returned with `auditDegraded: true` (except that a failed warn-mode `injection_detected` append is swallowed without marking the call or its receipt, though the client is then degraded), the event is written to the dead-letter file when that write succeeds (a sidecar-only failure, where the event was fsynced but its `.meta` write failed, still rejects the append and still writes a dead letter carrying the event's hash; under `audit.failClosed` the call is refused before its POST only when the failed record is the call's primary `llm_call` record; the same sidecar failure on a later record, such as the `settlement_shortfall` append after a capped post, is refused only after the charge has posted), and `usertrust verify` reports any dead-lettered event missing from the chain. If the dead-letter write fails too and leaves no bytes, the gap is visible only to `usertrust verify --receipts` with your own receipts (it sees a missing primary spend record, the receipt's own `llm_call` or action event, only; a lost auxiliary record such as a settlement shortfall, a detection, an implausible-usage or ambiguous-settlement record is invisible to it, as to `verify` and `health` when its dead letter was not written; a partial dead-letter line left by a short write is read as an unreadable entry, so `verify` reports INCOMPLETE), and `usertrust health` is blind there as well. With `trust()` and `audit.failClosed: true` the call is refused with `AuditDegradedError` instead, and whether it was charged depends on when the client's audit writer degraded. If the writer was already degraded when the call started, the call is refused at its start, before any policy check, hold, provider call or action runs (after the check that the client was not destroyed, and for an action after its cost input is validated): no hold, no spend, nothing charged. If the writer degrades during a call, the outcome depends on how the call ran: a non-stream call or action whose own audit record is written settles and is then refused after its charge posts; one whose own record fails is refused before the POST and not charged (the hold is released by a void request; the void is best-effort, so if the ledger refuses it the hold stays reserved until it expires, up to 300 s); a streamed call always settles before its record is written, so it may have been charged; wherever the settlement POST failed, the outcome is unknown. Treat an `AuditDegradedError` as possibly charged unless its message says nothing was charged. A retry does not undo a charge that posted: `interceptCall` claims the settle outcome before it POSTs and its outer catch voids only a hold still pending, so the posted transfer stays, and the retry is a new call with a new transfer id; on the same client it is refused at its start until the client is recreated. A `messages.stream()` call is refused only through its `.receipt`: await it, because the helper's iteration, `done()` and `finalMessage()` can still succeed. A client's writer stays degraded until the client is destroyed, so every later call on it is refused at its start in this way until the client is destroyed and recreated; the mark is per client, so another client on the same vault is not affected. `createGovernor()` and `usertrust-server` do not enforce `audit.failClosed`: they report `auditDegraded` and do not refuse.
</Callout>

## VaultNotInitializedError

Thrown when the `.usertrust/` vault directory does not exist.

```typescript
class VaultNotInitializedError extends Error {
  readonly path: string;
  readonly hint: string;
  readonly docsUrl: string;
}
```

**When it fires:** During `trust()` initialization, before any LLM calls.

**Hint:** `'Run "npx usertrust init" to create the vault directory.'`

## Error Summary

| Error | Failure Mode | LLM Call Forwarded? | Tokens At Risk? |
|-------|-------------|--------------------|-----------------|
| `InsufficientBalanceError` | Pre-call | No | No |
| `PolicyDeniedError` | Pre-call | No | No |
| `AccountNotFoundError` | Pre-call | No | No |
| `IdempotencyConflictError` | Pre-call | No | No |
| `LedgerUnavailableError` | 15.4 | No | No |
| `AuditDegradedError` | 15.3 | Yes when it fires after the provider call (the usual case, and a failed primary record under `audit.failClosed`); No when `audit.failClosed` refuses a call at its start on an already-degraded client | Settled and charged in the usual case; nothing is charged on a start-of-call refusal or a failed primary record (the hold is released by a best-effort void request, see above) |
| `VaultNotInitializedError` | Pre-call | No | No |

All pre-call errors are thrown before any interaction with the LLM provider. No tokens are consumed and no budget is affected.
