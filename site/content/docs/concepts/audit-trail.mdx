---
title: Audit Trail
description: SHA-256 hash-chained, append-only audit log for every governed LLM call.
---

Every governed LLM call produces an immutable audit event. Events are written to an append-only JSONL file where each event's SHA-256 hash covers the previous event's hash, forming a tamper-evident chain.

## Hash Chain Mechanics

Each audit event contains a `previousHash` field pointing to the hash of the preceding event. The event's own `hash` is computed over the deterministic canonicalization of the entire event (including `previousHash`). This creates a linear chain where modifying any event invalidates every subsequent hash.

```
Event 0: hash = SHA-256(canonical({ ...data, previousHash: GENESIS_HASH }))
Event 1: hash = SHA-256(canonical({ ...data, previousHash: event0.hash }))
Event 2: hash = SHA-256(canonical({ ...data, previousHash: event1.hash }))
```

The first event chains from `GENESIS_HASH` -- 64 zero characters (`"0000...0000"`).

## Deterministic Canonicalization

To ensure the same event always produces the same hash regardless of property insertion order or serialization quirks, usertrust applies deterministic canonicalization before hashing:

- Object keys are **sorted** recursively
- `undefined` values are **stripped** (keys with `undefined` are omitted)
- The result is JSON-stringified with no whitespace

This means `{ b: 1, a: 2 }` and `{ a: 2, b: 1 }` produce identical hashes.

## AuditEvent Structure

Each event in the chain follows this shape:

```typescript
interface AuditEvent {
  id: string;
  timestamp: string;
  previousHash: string;
  hash: string;
  kind: string;
  actor: string;
  data: Record<string, unknown>;
}
```

Events are stored as JSONL (one JSON object per line) in `.usertrust/audit/events.jsonl`. A sidecar file (`events.jsonl.meta`) tracks the last hash and sequence number for fast appends without re-reading the entire chain.

## One Writer per Vault

The audit chain has one writer per vault:

- **Within one process, clients share it.** Every `trust()` client and `createGovernor()` governor in a process that opens the same vault appends through ONE writer (one async mutex, one cached tail), so concurrent governed calls from any of them land on one linked chain.
- **Across processes, the advisory file lock keeps one.** A second process that opens the same vault does not get to write: its audit writes fail with an error naming the lock holder, and its events go to the dead-letter queue (below), which `usertrust verify` reports. Its calls still settle: only a `trust()` client with `audit.failClosed` refuses them instead; `createGovernor()` and `usertrust-server` never enforce `audit.failClosed`, and report `auditDegraded`. Give each process its own vault (`vaultBase`), or run `usertrust-server` and have every process call it.

Chain integrity holds for the one process that owns the vault; it is not shared across processes.

## Dead-Letter Queue

If an audit write fails, usertrust does **not** throw by default. Only a `trust()` client with `audit.failClosed: true` refuses the call instead (the default is `false`); `createGovernor()` and `usertrust-server` never enforce `audit.failClosed`. Otherwise:

1. The failed event is written to `.usertrust/dlq/dead-letters.jsonl` (fsync'd, with a checksum), unless that write fails too
2. The response is returned with an `auditDegraded` flag on the governance receipt, and the process gets a `USERTRUST_AUDIT_DEGRADED` warning
3. `usertrust verify` reports the vault INCOMPLETE (`complete: false`, exit 1) while a dead-lettered event is missing from the chain, and `usertrust health` reports it as critical. Both read the dead-letter file, so if the dead-letter write failed too (a full disk, say) neither sees the gap; `usertrust verify --receipts`, given your own receipts, does. No command yet puts dead letters back on the chain: keep the file

With `trust()` and `audit.failClosed: true` the call is refused with `AuditDegradedError` instead, and whether it was charged depends on when the client's audit writer degraded. If the writer was already degraded when the call started, the call is refused at its start, before any policy check, hold, provider call or action runs (after the check that the client was not destroyed, and for an action after its cost input is validated): no hold, no spend, and nothing is charged (the error's message says so). If the writer degrades during a call, the outcome depends on how the call ran. For a non-stream call or action, if its own audit record fails, the call is aborted before any money moves: the hold is voided and nothing is charged. If its record is written and the spend settles, and a later audit write for the call fails, the call is refused after its charge posts. A streamed call always settles before its record is written, so it may have been charged. Wherever the settlement POST failed, the outcome is unknown. Treat an `AuditDegradedError` as possibly charged unless its message says nothing was charged. A client's writer stays degraded from its first failed audit write until the client is destroyed, so every later call on it is refused at its start in this way, with nothing charged, until the client is destroyed and recreated (recreate it after fixing the audit directory). The mark is per client, so another client on the same vault is not affected. `createGovernor()` and `usertrust-server` do not enforce `audit.failClosed`: their receipts report `auditDegraded` and the call is not refused.

<Callout type="warn">
The dead-letter queue is a safety net, not normal operation. If events accumulate in the DLQ, investigate the underlying write failure (disk full, permissions, corrupt chain).
</Callout>

## Rotation

Audit receipts can be rotated on a daily or weekly schedule to prevent unbounded file growth. Configuration options:

| Option | Values | Default |
|--------|--------|---------|
| `audit.rotation` | `daily`, `weekly`, `none` | `daily` |
| `audit.indexLimit` | number | `10000` |

Rotated receipts are stored in kind-specific subdirectories under `.usertrust/audit/`:

```
.usertrust/audit/
  events.jsonl           # main hash chain (never rotated)
  events.jsonl.meta      # last hash + sequence sidecar
  index.json             # bounded receipt index
  spend/2025-01-15/      # daily-rotated spend receipts
  spend/2025-01-16/
```

The bounded index (`index.json`) keeps the most recent entries up to `indexLimit`, evicting oldest-first.

## Verification

The chain can be verified independently using either the built-in CLI or the standalone zero-dependency verifier:

```bash
# Built-in CLI
npx usertrust verify

# Standalone verifier (zero dependencies)
npx usertrust-verify .usertrust
```

Both tools re-compute every hash from GENESIS_HASH forward and confirm each event's `hash` matches the expected value. Any tampered, reordered, or missing event breaks the chain.

<Callout type="info">
The standalone `usertrust-verify` package intentionally duplicates all canonicalization and hashing logic from `usertrust`. It has zero dependencies -- only Node built-ins (`node:crypto`, `node:fs`, `node:path`). This ensures the verifier cannot be compromised by a supply-chain attack on `usertrust` itself.
</Callout>
